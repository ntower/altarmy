# CLAUDE.md

Conventions for AI agents working in this repository.

## Project

This is the Alt Army website (`altarmy-site`: a Python API and a React front end), which finds profitable crafting recipes and production chains for **World of Warcraft: Forever**. Items and recipes come from client DB2 tables (wago.tools CSV exports) loaded into the database (Postgres on the site, SQLite in development and tests); auction house prices come from the full scans players take with the Alt Army addon and upload; the engine ranks recipes by profit (buy or craft reagents, then sell via vendor, AH minus the 5% cut, or disenchant). See `README.md` for usage and roadmap.

## Layout

- `src/altarmy_site/versions.py` – the game versions (`tbc` TBC Anniversary, `forever` WoW: Forever): each `GameVersion` names its `data/<version>/` data files, wago.tools product, interface number, WoW flavor folder (`_anniversary_`, `_classic_beta_`), level and skill caps (`max_level`, `max_skill`), AH cut and postage, whether its prices are first-party (`first_party_prices`, Forever: from Alt Army's scans and hand-set prices alone), and what reputation takes off at vendors (`reputation_discounts`: (standing, percent) pairs; Forever 10% from Honored)
- `src/altarmy_site/db.py` – `Database(url)`: the engine factory (SQLite or Postgres via SQLAlchemy Core), migrated to the newest Alembic revision and `game_versions` registered on first use; `default_url()` (`DATABASE_URL`, else `data/altarmy.sqlite`); `Database(url, migrate=False)` never migrates (hosted instances: the deploy's migrate job does, and `upgrade` holds a Postgres advisory lock); pool sizes from `DB_POOL_SIZE`/`DB_MAX_OVERFLOW`; `upsert` (dialect-specific ON CONFLICT), build and row-count helpers (settings live in `users.py`)
- `src/altarmy_site/schema.py` – every table as a Core `Table` on one `MetaData`; `src/altarmy_site/migrations/` – Alembic env and revisions (`alembic.ini` at the root for the CLI); `tests/test_migrations.py` checks they match `schema.metadata`
- `src/altarmy_site/auth.py` – `User(uid, tier, admin)`, `user_from_claims` (tier `free` iff the Firebase `sign_in_provider` is `anonymous`; `admin` iff a linked token carries the custom claim `admin: true`), `FirebaseConfig.from_env` (ValueError without `FIREBASE_PROJECT_ID`), the `TokenVerifier`, `AccountAdmin` and `AdminRoster` protocols and `FirebaseVerifier` (firebase-admin, in the `ui` extra; verifies tokens, deletes users, grants/revokes/lists the admin claim (`set_admin`, `admins`); honours `FIREBASE_AUTH_EMULATOR_HOST`)
- `src/altarmy_site/users.py` – `ensure_user` (row on first sight, follows tier changes, sets `linked_at`), `delete_user` (cascades; nulls `price_snapshots.uploader_uid`), typed `UserSettings` (selection, `data_version`, time settings) per (user, game version); `trust`/`adjust_trust` (`users.trust_score`: halved per quarantined scan, +0.1 per accepted screened one)
- `src/altarmy_site/uploads.py` – uploaded addon files: `ingest` (Alt Army replaces the uploader's characters via `service.replace_characters` and, where prices are first-party, records the auction house scans the file carries, `_record_books`: each for the house of the realm and faction the scan names, at the scan's own time, oldest first; a scan already recorded or older than the house's newest is passed over and left out of `Imported.realms`, since the file holds the last few scans and is sent again whenever it changes; an Auctionator file is refused there, `FIRST_PARTY_ONLY`. Elsewhere (TBC) Auctionator records every realm with prices, each key resolved alias first, then the uploader's matching character group, then parsed), `scan_time` (a time clamped to 30 days back and never the future), `decompress` (gzip, `MAX_BYTES` 32 MB), `record_upload`/`recent` history, `check_rate` (`RATE_LIMIT` 60/hour); every scan is screened with the uploader's trust (`RealmPrices.quarantined`, "not used" in the detail; the upload stays `accepted`)
- `src/altarmy_site/watch.py` – the CLI watcher (`altarmy-site watch`, no database): `find_files` (both versions, Alt Army first; `version_of` by flavor folder; no Auctionator file where prices are first-party), `changed` against a JSON state of mtimes, gzipped multipart over urllib (`Transport` injectable), `sync_once`, `run` (backoff; stops on `signin.SignedOut`); uploads send an `Auth` (a callable giving an ID token: `signin.Credentials`); standard library only (the WoW folder finders live in `wowfiles.py`, re-exported by `prices`)
- `src/altarmy_site/book.py` – pure, standard library only: the auction house's order book from the Alt Army addon's full scans (`AltArmyTBC_AuctionBook`, its own SavedVariable in `AltArmy_TBC.lua`, written by the addon's `Data/Auctions/AuctionScan.lua` and `AuctionBook.lua`: per scan `{t, realm, faction, complete, listings, bidOnly, source, items}`, `items` being `<itemID>:<unit price>*<units>*<listings>,...;...`, at most 12 levels per item then a `~` tail). `read` (complete scans oldest first, read with `luasv.parse_assignment`; malformed is a ValueError), `Level`/`Ladder`, `encode`/`decode` (how a ladder is stored, with each level's `age`), `cost` (what `qty` units cost bought cheapest first, and the units short), `market_price` (the unit price 15% into the listed units), `aged`, `sold_between` (units gone at or under the cheapest price still listed were bought, those gone from behind it cancelled; a listing new since the first scan and cheaper than anything in it doesn't count for that cheapest price). the tests read the addon's golden `addon/spec/fixtures/auction_book_v1.lua` (`tests/addon_fixtures.py`), so the two sides can't drift apart
- `src/altarmy_site/signin.py` – the watcher's and Alt Army Sync's email sign-in, standard library only: `fetch_config` (the site's `/api/config`), `sign_in`/`sign_up`/`refresh` against Firebase Auth's REST API (or the emulator the config names; every request sends the site as its Referer, since the browser key only answers the site's origins), `Credentials` (a refresh token that hands out ID tokens, refreshing 5 min early; `on_change` when Firebase rotates it), `SignInError` (readable reasons), `SignedOut`, `Unreachable`; `load_saved`/`save` keep only the refresh token per site (`~/.altarmy/watch-auth.json`), never the password. There are no API keys: the `api_keys` table is unused and dropped with `local_sync` in the next revision
- `src/altarmy_site/paste.py` – pure decoder of the Alt Army addon's export string (`AAX1:` + LibDeflate's printable encoding of raw DEFLATE of `V|`/`C|`/`P|`/`T|`/`R|` lines (`T|<spell id>|<rank>`: a Legacy talent; `R|<faction id>|<standing>`: a standing with a city faction, other factions' lines passed over, none from older addons); `decode`, `Export.game_version` from the client's interface). Format v2's `C|` line ends with the character's GUID (`Character.guid`, "" for characters saved before the addon stored GUIDs; not stored in the database); v1, from older addons, has none and is still read, but a v1 name that is a GUID (addon 2.1.3's export wrote its storage key) is a ValueError asking for a newer addon. The addon's `addon/AltArmy_TBC/Data/ProfitExport.lua` writes it; the tests read its golden `addon/spec/fixtures/profit_export_v2.txt` (`tests/addon_fixtures.py`), so the two sides can't drift apart (`tests/fixtures/altarmy_export_v1.txt` keeps v1 covered)
- `src/altarmy_site/tray.py`, `tray_core.py` – Alt Army Sync, the Windows uploader (`altarmy-sync`; the `tray` extra: pystray, Pillow): the watcher in a thread, a sign-in dialog (tkinter: sign in or create an account; `tray_core.form_problem` checks it), Start with Windows (HKCU Run), one instance per user; `tray_core` is its pure, tested part (`Target`: the live site by default, `--staging` or `--server URL` another, each with its own settings file, log, mutex and Run entry; `~/.altarmy/sync.json`: email, refresh token, the release last announced; status line, autostart command with the target's flags; `check_for_update`: the newest `sync-v*` GitHub release if newer than `VERSION`, which `build_sync.py --version` stamps into the exe, "dev" from source and never checked; the tray asks every 6 h, notifies once and adds Update available to its menu). Sync's modules (`tray`, `tray_core`, `watch`, `signin`, `wowfiles`, `versions`) import only the standard library, each other and the tray extras (`tests/test_sync_imports.py`), so `versions` holds `AH_CUT` and `MAIL_POSTAGE` (re-exported by `engine`). `scripts/build_sync.py` (the `build-tray` extra) makes `dist/altarmy-sync.exe`; `.github/workflows/sync.yml` publishes it as a GitHub Release on a `sync-v*` tag, and the Manage page links the latest
- `src/altarmy_site/gamedata.py` – where the game data comes from, shared with the addon: standard library only and no package imports (the addon's `generate-recipe-data.py` and `build-recipe-server-facts.py` and the monorepo's `game_data.py` load it by its path; `tests/test_gamedata.py`): `latest_build`, `download_table`, the emulators' rolling releases (`EMULATORS`, `latest_release`, `world_db`: a release neither cached nor the newest is a LookupError), the pins (`data/game-data.json`: per version the DB2 build and the emulator release the committed data came from; `read_pins`, `write_pins`, `Pin`), and the cache layout (`REPO_CACHE`, the monorepo's `.cache/`: `wago/<build>/`, `emulators/<emulator>/<release>/`; the CLI's `--cache` default; the hosted jobs pass `/tmp/cache`)
- `src/altarmy_site/ingest.py` – download DB2 CSVs through `gamedata` (`TABLES`, plus `OPTIONAL_TABLES` a client may lack: a 4xx is cached as an empty file and reads as no rows) and load one version's game data into the database; `output_count` reads either client's SpellEffect encoding; `fingerprint` hashes the ingest code (`FINGERPRINTED_MODULES`) and the version's hand-maintained CSVs, stored as `game_versions.ingest_fingerprint` (revision 0020) by every load, so the ingest job reloads a loaded build when either changed; `item_tooltips` computes every item's tooltip numbers and lines (`game_tables`, `item_spec` into `itemstats`); `recipe_items` (which items teach each spell, into `recipe_items`) and `item_sources` (the version's `recipe_item_sources.csv` into `item_sources`; revision 0021); `zone_boxes` (the client's zone maps), `zone_at` (the smallest box around a spot: cities) and `spawn_zone` (the smallest that holds a spot well inside, else the one it is nearest the middle of, continents never: spawns)
- `src/altarmy_site/itemstats.py` – pure item tooltip formulas: stat values from ItemSparse's allocations x RandPropPoints, armor (ItemArmorTotal x ItemArmorQuality x ArmorLocation, shields, bonus armor), weapon damage (the ItemDamage* tables), rendered as the white stat lines and green Equip lines (`STAT_NAMES`, `EQUIP_TEXT`, `RATINGS`: level-60 divisors hard-coded, since GameTables are not served; other level caps show ratings raw)
- `src/altarmy_site/spelltext.py` – pure renderer of item spell effects (the Use / Equip / Chance on hit lines): `expand` fills a Spell description's `$` variables (`$s1`, `$o1`, `$d`, `$@spelldesc`, `${...}` arithmetic, `$?` conditionals take the else branch, unknown tokens stay as written) from a `SpellData` that ingest's `spell_data` builds for the item spells and what they reference; `render_effect` adds the cooldown to Use lines. `ingest.item_effects` reads Forever's ItemXItemEffect link or TBC's `ParentItemID`. `scripts/spotcheck_tooltips.py` compares computed lines with Wowhead's Classic tooltips (network, dev only)
- `src/altarmy_site/engine.py` – pure profit/chain logic (no I/O). Every tree `Node` lists its `options` (vendor, ah, `craft:<recipe id>`, cheapest first) and the `option` taken; `Result.sell_options` gives each exit's best profit. `evaluate(recipe, choices)` takes user picks keyed by tree path (`r.0`, `r.0.1`; `sell` for the exit); subtrees with a pick skip the memo. With a `TimeModel(config, city)` (`Market(time=)`), nodes, options, steps and results carry seconds (all `compare=False`), options and exits are ranked by copper plus `time_value` x estimated seconds (`Market._effective`; a time value of 0 changes no plan), and `Result.timing` (lazy, like `steps`: `rank()` never times) routes the plan through the city (`time_result`); `Result.rate` is copper per hour. The model's city also prices vendor buys by the buyer's reputation (`Market(reputation_discounts=)`, `Crafter.reputations`, `vendor_price`, `Node.rep_discount`; `vendor_holders`, `cost_in`, `city_prices`, `recipes_using`: see Reputation discounts below). An item in `Market(books=)` is bought up its ladder (`_ah_cost`, `book.cost`), so its cost depends on the quantity; units the book is short of cost its dearest price (`Node.short`, `Result.short`); a plan's branches buying the same item share the ladder (`_share_books`, after the plan is chosen); an item with neither a book nor a price has no AH option; a disenchant material in `Market(sell_depth=)` (`store.load_priced` fills it from the listings with `prices.sale_depth`) sells on the AH only as many units as its market has shown it takes, the rest at a vendor (`Market._disenchant_shortfall`, off the disenchant exit's revenue for the run's units; `Exit.value` stays per unit)
- `src/altarmy_site/prices.py` – the price store and its sources: auction houses (`find_auction_house`, `auctionator_auction_house`, `unnamed_auction_house`), `record_book` (an Alt Army scan: every item's ladder into `price_current`, levels aged, items it no longer has unlisted, observations only for news, inferred sales into `price_sales_daily` when the scan before is at most `SALES_GAP` old, with `pairs`: the pairs of scans units were seen bought in (revision 0023); a scan no newer than the house's newest is `stale`; returns `BookRecorded`), `load_books` (what plans buy from: without levels first seen in the newest scan under `STRAY` of the 7-day median, or before a baseline under `STRAY` of the next level's price), `book_sell_price`, `record_snapshot` (every other source; writes observations only for news and moves `price_current`; a newer quantity alone updates `price_current.quantity` in place), `record_daily` (pools uploaders' days: min low, max high, max available), `prune`, `load_current`, `load_buy_and_sell` (the engine's buy and sell prices; `first_party=` reads only `FIRST_PARTY` sources), `sale_depth` (what a market has shown it takes: the more of a week's sales seen and the units listed at or under a price; `service.ah_sale` and disenchant materials), `load_listings` (`Listing`: cheapest listing, quantity, ladder, sale rate, and what `confidence` reads: source, `listed`, `seen_at`, 7-day median and its days, sale price; `thin_market`, `THIN_UNITS`), `watched_hours` (the hours between a house's accepted Alt Army scans at most `SALES_GAP` apart over the last `SALES_DAYS`: the only stretches whose sales are seen), `confidence` (how far an AH sell price can be trusted for a plan's units: high when the sales seen cover them in at least two pairs of scans (`Listing.sold_pairs_7d`) of a house watched `WATCHED_ENOUGH_HOURS`, medium when fewer (`few_sold`) or all in one pair (`one_pair`), else low when unlisted, a median from under `CONFIDENT_SCAN_DAYS` days, `WATCHED_ENOUGH_HOURS` watched with too few sales, or a thin market, else medium; hand-set prices high; `Confidence` names the reason and its numbers, and `flags` every doubt on its own, most actionable first: `lone`, `thin`, `sold_out`, `unlisted`, `few_days`, `unwatched`, `one_pair`), `auction_houses` (with price counts), `coverage`, `stats`, `daily`; `screen`/`baseline` (quarantine), `record_auctionator(..., trust=)` and `record_screened` return `Recorded`; `record_daily_observations`; `set_price` (a manual price)
- `src/altarmy_site/jobs.py` – runs of the scheduled CLI jobs in `job_runs` (revision 0010): `recording(database, job, game_version)` wraps a job (a row at start, then ok/failed and what it said via `Run.say`, each in its own transaction; `Run.warn` says it as a JSON line Cloud Logging reads as a WARNING with an `alert` tag; `sys.exit` with a message or non-zero code is a failure; runs unrecorded before the table exists), `recent`, `latest`, `late` (older than 2x `CADENCE`, which mirrors `deploy/setup.sh scheduler` and names the scheduled jobs; `schema.JOBS` still allows the removed ahledger job's old runs), `running` (unfinished and younger than `TIMEOUT`, the jobs' 30 min task timeout)
- `src/altarmy_site/launch.py` – starting a job on demand (the Admin page's Run now): `run_ingest` (the ingest job's `--only-if-new` work: the pinned build, recorded; the CLI calls it too), `Launcher` protocol, `CloudRunJobs` (hosted: POSTs the Cloud Run Admin API's `jobs/<JOB_PREFIX>-ingest-<version>:run` with the service account's credentials (google-auth, via firebase-admin); `deploy.sh` sets `CLOUD_RUN_LOCATION` and `JOB_PREFIX` on the service, `deploy/setup.sh job-runner ENV` grants it `roles/run.invoker` on the ingest jobs), `InProcessJobs` (development: a thread of the API, one at a time), `from_env` (Cloud Run when both are set, else in-process on SQLite, else none: a hosted service never runs a job's work itself)
- `src/altarmy_site/merge.py` – the merge (`altarmy-site merge`, hourly Cloud Run job): `price_daily.median` and `price_current`'s 7-day columns (a scan's sample is its market price, else the minimum buyout), `sale_price`, `sale_rate` and `sold_pairs_7d` (the pairs of scans those sales were seen in) from the last 7 days of `price_sales_daily` (`MIN_SALES`), bumping `auction_houses.price_version` when anything moved; once `price_observations` reaches `PARTITION_AT` rows (5M) the CLI's merge logs a `Run.warn` tagged `PARTITION_ALERT`, which the log-based alert policy from `deploy/setup.sh alerts` posts to Discord (`alerts.py`) at most once a day
- `src/altarmy_site/cloudlog.py` – logs on Cloud Run (`K_SERVICE` or `CLOUD_RUN_JOB` set; elsewhere `configure` changes nothing): `JsonFormatter` (one JSON line per record with its `severity`; a record with an exception carries its traceback and Error Reporting's `@type` and `serviceContext`), `configure` (the root's and uvicorn's handlers, uncaught exceptions; called by `api.create_app` and `cli.main`; uvicorn run with an app object needs `log_config=None` afterwards)
- `src/altarmy_site/alerts.py` – the Discord relay (`altarmy-site alert-relay`, Cloud Run service `altarmy-alerts`, `deploy/setup.sh discord`): Cloud Monitoring's alert policies and Error Reporting (which notifies only email, Slack and webhooks, not Pub/Sub) notify the basic-auth webhook channel "altarmy Discord" that calls it; the service is public, so `POST /` answers 401 with a `WWW-Authenticate` challenge without `USERNAME` and the password (`RELAY_PASSWORD`, secret `alerts-relay-password`; `authorized`, constant-time); `discord_message` (pure: an incident as one embed, red open, green resolved; an Error Reporting error with its traceback and a link to its group; anything else as its JSON), 400 for what isn't JSON, 502 when Discord fails (a notification then is lost: no retries), `webhook_post` (`DISCORD_WEBHOOK_URL`, secret `discord-webhook`)
- `src/altarmy_site/signals.py` – price signals through Firestore: `priceSignals/<auction house id>` holds only `{version, game_version, updated_at}` (the house's `price_version`, never prices); `Signals` protocol, `FirestoreSignals` (firebase-admin, lazy client, the `altarmy-<project>` app; `FIRESTORE_EMULATOR_HOST` in development), `NoSignals`, `for_project`/`from_env` (none without a project or with `PRICE_SIGNALS=off`), `publish_all` (logs failures, never raises). Published only after the transaction that bumped the version committed: `POST /api/uploads` (a background task) and the `merge` job. `firestore.rules`: signed-in users read `priceSignals`, nobody writes from a browser
- `src/altarmy_site/auctionator.py` – pure parser for Auctionator's SavedVariables (TBC's prices; Forever's come from `book.py`) (Lua string holding CBOR): per item an `ItemPrice` (latest minimum buyout, per-day `DayStats` high/low/available)
- `src/altarmy_site/timing.py` – pure play-time model (no engine import; the engine imports it): `TimeConfig` (seconds per action, `batch` crafts per session, `time_value` copper per hour of play, run speed, detour; `config_from_dict` strict, `config_from_json` lenient, `config_changes` what is stored), `CityMap` (locations in yards, vendors' stock and the faction each vendor's prices follow (`vendor_reputations`, `sellers`, `reputation_of`), hub, `overrides`, `zone`: its zone map's world box and AreaTable `area` id, for map coordinates; `from_dict`, `seconds`, `nearest`, `vendor_for` (optionally among some sellers), `trip`; memoized, shared across threads), `ANYWHERE` (the one-spot city when a version has no presets), `station_kind` (a SpellFocusObject name as a location kind), `Block`/`route`/`time_blocks` -> `Timing` (fixed and per-craft seconds, `breakdown`, `legs`, `unsold`, `missing`, `per_hour`)
- `src/altarmy_site/cities.py` – pure builder of city presets (`CITY_SPECS`, `build_city`) from vmangos spawns (`vmangos.city_centre`, `npcs_near`, `objects_near`, `vendor_stock`, `vendor_factions`: a preset's `vendor_reputations` name the city-faction vendors' factions); `scripts/build_cities.py` writes `data/forever/cities/*.json`, keeping each preset's hand-tuned `overrides`; `scouted_mailboxes`/`add_scouted_mailboxes` add the mailboxes the user's frellscout addon (`../frellscout`) recorded in game to those `overrides` (`scripts/import_mailboxes.py`), skipping any within 10 yd of a known one (vmangos has only Classic's)
- `src/altarmy_site/talents.py` – the Legacy talents (WoW: Forever) that change profits, by spell id (`LEGACY_TALENTS`: Master Chef, Bartering, Working Overtime); `extra_results`/`vendor_discount`/`skill_bonus` turn a character's (spell id, rank) pairs into `engine.Crafter` fields, `known` lists them for the API
- `src/altarmy_site/reputation.py` – pure: the reputations that change vendor prices, `CITY_FACTIONS` (the eight home factions by `Faction` id: the six cities' plus Gnomeregan Exiles and Darkspear Trolls, whose vendors stand in other cities); `city_standings` keeps a character's standings with those, `vendor_discounts` turns them into (faction, percent) by a version's schedule
- `src/altarmy_site/luasv.py` – pure generic parser for SavedVariables files (`Name = <Lua table>` statements); nesting capped at `MAX_DEPTH`
- `src/altarmy_site/altarmy.py` – pure reader for the Alt Army addon's `AltArmy_TBC.lua`: characters, professions, learned recipe ids (= `recipes.spell_id`); characters are keyed by GUID since the addon's character data v3 (by name before), so the name is the entry's `name` field (the full name), else the key; entries with the same `guid` or name are one character, the newest `lastUpdate` winning (a bare first name, which pre-v3 addons saved for every "First Surname", is not matched); never-scanned stubs (no name, class or faction) are skipped; `Character.reputations` are the entry's `Reputations` standings with the city factions; `groups` by realm/faction, `crafters`
- `src/altarmy_site/store.py` – `load_market(conn, game_version, auction_house_id, ah_cut=, mail_postage=)`: database rows to engine dataclasses; characters (`save_characters` replaces all, `upsert_character`/`delete_character` one) and AH blocks per user and version; `profession_names` (without `HIDDEN_PROFESSIONS`: class skills and a test line DB2 gives recipes)
- `src/altarmy_site/ratelimit.py` – pure in-memory sliding-window `RateLimiter` (per instance), `Limits`/`HOSTED_LIMITS` (per IP 300/min, per uid 120/min), `client_ip` (first `X-Forwarded-For` entry: right through Firebase Hosting, spoofable on the direct run.app URL)
- `src/altarmy_site/service.py` – web use-cases (every per-user function takes `user_uid` after `conn`): `MarketCache` (per version, one `Market` per auction house; rebuilt after `invalidate()` or when `store.market_stamp` (build, `game_versions.loads`: bumped by every `db.set_build`, so loading the same build again counts (revision 0018), newest accepted snapshot id (a quarantined one changes nothing a market reads), `price_version`) moved, checked at most every `STAMP_TTL` s, so other instances' uploads, the ingest job and the merge show up; a check or rebuild holds only its house's lock, never the cache's, and while one runs other requests keep the market there is unless they know of newer prices; `invalidate()` bumps the house's generation, so a rebuild that read before it is handed to its caller but not kept; `get_held` adds the market's token, (auction house, stamp)); `RankCache` (the last `RANK_CACHE_SIZE` (64) full rankings, keyed by the market's token (`Held.token`), so a rebuild on the same data keeps them; a skill workspace load holds about 16 MB, a gold list about 4 MB, so it isn't larger in 1 GiB; `/api/rank` slices `top` from it, so paging doesn't re-rank; `api._ranked` reads and fills it through `Flights`: identical rankings at once (several tabs, a refetch) are worked out once, the others waiting for the first); `search` over the selected realm/faction's characters (`engine.recipes_for_characters`: learned recipes, plus with `unlearned` "train" those a character can train: taught by one of the chosen `sources` (`Recipe.source`: trainer, recipe, bop) and needing at most `look_ahead` (0 to `MAX_LOOK_AHEAD`, 50; the slider steps by 5) more skill than they have (`engine.Learning`, `engine.can_learn`, `Recipe.required_skill`), or with "all" every recipe of their professions whatever teaches it: the search's Recipes radio and its sub-options; chains only sub-craft through those; without characters every recipe, for one unnamed crafter), selling only via the allowed exits and keeping what an `engine.Filters` (min/max cost, profit, ROI) accepts; `evaluate`: one recipe with the user's `choices`; both plan per group of cities that charge the characters differently and keep each recipe where it pays best (`city_groups`, `best_of`, `city_worth`; see Reputation discounts); realm/faction `selection` (saved if it has characters or an auction house, else the biggest group, else `prices.freshest_auction_house`) and its auction house (`selected_auction_house`); `select` takes a group or any named auction house; `replace_characters` (imports: forgets a selection the new characters aren't on), `delete_character`; `data_version`/`bump_data_version`; game data update (`update_game_data`, the ingest job's `--only-if-new`)

Use the project venv (`.venv`); do not install packages globally. If it is missing: `python -m venv .venv`, then `.venv\Scripts\python -m pip install -e ".[dev,ui]"` (add `,tray,build-tray` for Alt Army Sync). Front-end packages live in `frontend/node_modules` (`npm ci` in `frontend/`); the root `package.json` only holds dev tooling (`npm ci` in the root).

- `python scripts/check.py` – ruff lint, ruff format check, mypy (strict), pytest, then regenerates the OpenAPI spec and TS types and runs oxlint, vitest and `tsc -b && vite build`. **Run before considering any change done.** Pass `--skip-frontend` for Python-only iteration.
- `ruff check . --fix`, `ruff format .`, `mypy`, `pytest` – individual Python tools; `npm run lint|test|build|dev|gen-types` in `frontend/`.
- Postgres: set `TEST_DATABASE_URL` (e.g. `postgresql+psycopg://postgres:postgres@localhost:5432/altarmy_test`) and run `pytest`; the tests drop and recreate that database's `public` schema, so never point it at real data. CI does this on every push.
- Schema changes: edit `schema.py`, then `alembic revision --autogenerate -m "..."` (uses `DATABASE_URL`, else `data/altarmy.sqlite`; point it at a database migrated to head), review the revision (SQLite needs batch operations; `env.py` renders them) and keep `test_migrations.py` green on both databases.
- Deploy: see README's "Deploy" (Git Bash). Creating, changing or deleting cloud resources is visible and billed: show the command and get the user's OK first; read-only gcloud is fine.
- Dev loop: `npm run dev` in the repo root first kills whatever still listens on the dev ports (`predev`: `scripts/free-ports.mjs`: the emulators' 9099, 8080, 9150, 4400, 4500, the API's 8600, Vite's 5173), then runs the Firebase Auth and Firestore emulators (`scripts/dev-auth.mjs`: `firebase-tools`, a root dev dependency; needs Java; started again, up to 3 times, when the Firestore emulator hangs before opening 8080), the API (`scripts/dev-api.mjs`: `altarmy-site serve --reload` with the venv python on :8600 (`--no-reload` for one process; a reload drops the market and rank caches), signed in against the emulator; once it answers, in the background `ingest --only-if-new` for both versions (the pinned build, a no-op unless the pins, ingest code or CSVs moved), unless `--no-ingest`, then `merge` for the price statistics, unless `--no-prices`; prices themselves come from uploads) and, once both answer, Vite on :5173, which proxies `/api` to it. It is the site's code: there is no other mode. A fresh database needs `altarmy-site ingest` first.

## Conventions

- **User-facing text says "upload", never "import"**, for characters and scans alike (Upload your characters, Auto-upload, Characters uploaded). Code identifiers such as `AutoImport.tsx`, `onImported` and `auto_import_at` keep their names.
- **Money is integer copper** everywhere (prices, costs, profit), including the JSON API. Format only at the display edge: `format_money` in Python (CLI), the `Money` component (`frontend/src/components/Money.tsx`, coin icons) in the front end.
- **Admins are a Firebase custom claim** (`admin: true`, set with `altarmy-site admin grant <email>`), never a `users` column or an HTTP route; a token shows a grant once it is refreshed (sign out and in). Admin routes take `AdminUser`. Against the Auth emulator (`FirebaseConfig.emulator_host`, i.e. `npm run dev`) every user is an admin; `npm run dev:staging-auth` uses the real claim.
- **User state is per user**: characters, `user_settings` and `ah_blocked` carry `user_uid`; store/service/users functions take it right after `conn`. Never gate on tier inside service code: tiers are the API's dependencies. The `"local"` users row that revision 0002 creates is a leftover of the removed local mode (`local_sync`, unused, is dropped by the next revision).
- **Uploads are untrusted**: on bad input the parsers must only raise `ValueError` (the API's 400); `test_mangled_files_only_raise_value_error` fuzzes them. Never store an uploaded file.
- **Migrations run once per deploy** (`altarmy-site migrate` as a Cloud Run job, before the service); hosted instances never migrate. Keep revisions safe for the previous release's instances still serving (additive first).
- API handlers are plain `def` (FastAPI runs them in a threadpool) and open their own connection per request (`database.begin()`); never share a connection across threads.
- **Storage is SQLAlchemy Core** (no ORM) against `schema.py`, and must work on SQLite and Postgres: no raw SQLite-only SQL (`INSERT OR REPLACE`, `PRAGMA`) outside `db.py`'s engine setup; use `db.upsert`. Functions taking a `Connection` never commit: the caller owns the transaction (`Database.begin()` in the API and CLI; tests use an autocommit connection). Order query results explicitly; row order is not insertion order on Postgres.
- After changing API models or routes, regenerate `frontend/openapi.json` and `frontend/src/api/schema.d.ts` (`check.py` does this) and commit both.
- **Keep `engine.py` pure**: no file, DB or network access. Load data in `store.py` and pass plain dataclasses in.
- **Type annotations are required**; mypy runs in strict mode over `src` and `tests`, and the front end uses TypeScript `strict`.
- Prefer red-green-refactor: write a failing test first, then make it pass. Ingest tests use fixture CSVs, never the network. API tests use FastAPI's `TestClient`; front-end tests use vitest + Testing Library with `fetch` stubbed (`frontend/src/test/utils.tsx`).
- Line length is 110; let `ruff format` handle style.

## Data gotchas

- Development and tests keep **one SQLite file** (`data/altarmy.sqlite`) for both versions, the same schema as Postgres. Game data is keyed by `game_version`; `user_settings` (selection, `data_version`), characters and `ah_blocked` by `user_uid` and `game_version`; item and recipe ids are only meaningful within one version. The pinned/loaded build is `game_versions.build`. `recipe_reagents.slot` keeps DB2's reagent order, which the flow chart's choice paths (`r.0`, `r.1`) depend on.
- Disenchant results are server-side loot data and are **not** in DB2. Without a version's `disenchant.csv`, disenchant is ignored. Do not invent drop tables. Which items can be disenchanted is in DB2: ItemSparse `Flags_0` bit `0x8000` (NO_DISENCHANT: Enchanting's wands, PvP rank gear) makes `items.disenchantable` False (revision 0016; true in older databases until the next game data update), and `Market._disenchant_rows` gives such an item no disenchant exit.
- **Arcane Salvager** (WoW: Forever; Enchanting recipe spell `service.ARCANE_SALVAGER_SPELL` 1263056): near it a disenchant has `engine.ARCANE_SALVAGER_BONUS` (10%, the players' understanding, unverified) chance of a second roll of the same table. `/api/rank`'s and `/api/evaluate`'s `arcane_salvager` (in the rank cache key) -> `Market(arcane_salvager=)` scales `_expected`, so every disenchant value, its `Material.value`s and flips are 1.1x; a `Material`'s counts still describe one roll. No station trip is timed. `Characters.arcane_salvager` (`service.knows_arcane_salvager`: any uploaded character knows the recipe) is the UI's default.
- **Essence conversions** (`recipes.kind` `convert`, revision 0017; `Recipe.is_conversion`): an item's Use effect that consumes it and casts a spell creating another item, its reagents (if any) more of the same item, both items disenchant results (`ingest.conversions`; so none without `disenchant.csv`). Id `ingest.CONVERSION_ID_BASE` + spell id, skill line 0, skill name "" (left out of `profession_names`), input count 1 + the spell's reagents. Anyone converts (`crafters_of`, `recipes_for_characters`), it never skills up (`can_skill_up`, `expected_skill_ups`), `Market.rank` skips it without `include_trivial` or with `skill_crafters`, and `Market._sell_kinds` sells it only when `disenchant` is an allowed exit, then on the AH whether or not `ah` is. Chains use it as a `craft:<id>` option (always); `_craft` buys a conversion's input only (no chain below it, which would go round in circles). `Node`/`Step`/`Option.convert` and `RankResult.kind` tell the UI to say Convert.
- **Buy-and-disenchant flips** (`Recipe.kind` `flip`, `Recipe.is_flip`; `Recipe.anyone` covers both no-profession kinds): `Market` makes them itself (`_flips`, replacing any in the recipes it is given, so narrowed markets agree), one per item with `_disenchant_rows` that can be bought on the AH (`_listed`: its counted ladder's units, else 1 with a plain price), id `engine.FLIP_ID_BASE` + item id, reagents `((item, 1),)`; never in the database or `_by_output`. `evaluate` caps a flip's crafts at `_listed` (no `short` units), `_sell_kinds` allows only `disenchant` (and only when allowed), `_craft_seconds` is 0, `plan_steps` emits no craft step for its root and `Node.flip` lets the flow chart sell the bought node directly. Otherwise as conversions: anyone, no skill-ups, skipped when skilling up.
- **Enchants cast for the skill point alone** (`recipes.kind` `enchant`, `Recipe.is_enchant`; no migration: the kind is free text): a profession spell with reagents and SpellEffect `Effect` 53 (`ingest.EFFECT_ENCHANT_ITEM`) that creates no item, stored with `output_item_id` 0 and output count 1, otherwise as a craft (SkillLineAbility id, trivial ranks, `learn_skill`, `source`). Forever has 179 for Enchanting and 3 for Engineering. It is a profession's recipe (not `Recipe.anyone`: learned or trainable like a craft), never in `_by_output`, and its only exit is `engine.SKILL_EXIT` (`skill`, value 0, not among `ALL_EXITS`), which nothing else has: `Market._sell_kinds` allows it only when `skill` is among the market's exits, so enchants rank only where asked for. Revenue 0, profit = −cost, ROI −100%; `_final_crafters` always keeps only crafters it can skill up (whatever `include_trivial` or a `final_crafter` say); `plan_steps` ends with the cast (no sell step), the root `Node` and its craft `Step` are named after the spell with `enchant` set. `/api/rank` and `/api/evaluate` take `skill` in `exits`; `RankResult.kind` `enchant` has `output_name` = the spell's name. The rod an enchant needs and the item enchanted are not modelled. In the UI `skill` is sent whenever, and only when, the setup skills up Enchanting or Engineering itself (`AimSearch`'s `ENHANCING`; nothing to tick, the climb takes a dead-loss cast only where nothing gives the point cheaper); `ResultsTable` says "Skill only", the step list "Cast … N times", and the flow chart has no sell node.
- DB2 does not say which vendors sell which items. `data/<version>/vendor_items.csv` (unlimited stock, no condition, no token cost, spawned vendor) says which; the per-unit price is `items.buy_price / items.buy_count` (DB2 `BuyPrice` / `VendorStackCount`), rounded up. The engine buys each reagent from the cheaper of vendor and AH (ties go to the vendor). DB2's `BuyPrice` is set on nearly every item, so it alone does not mean a vendor sells it.
- `recipes.min_skill` currently comes out as 1 for every real recipe, so do not rely on it. The skill a recipe is learned at is `recipes.learn_skill`: the RequiredSkillRank of the recipe item teaching its spell (ItemEffect trigger 6, `ingest.learn_skills`; about 3/4 of Forever's recipes), else the skill the trainer asks for (`trainer_costs.csv`'s `req_skill`, vmangos' `npc_trainer.reqskillvalue`, the same at every trainer; DB2 lacks it), less its `yellow_shift`: vmangos' skills are vanilla's, and Forever moved many recipes' colours 5-45 points lower, so `ingest.trainer_costs` teaches a recipe as much earlier as its yellow moved against TBC Anniversary's (`ingest.yellow_shifts`, worked out by `scripts/build_vendor_items.py` against `--reference-build`, the TBC pin, and committed in the CSV), never below 1; the user's characters knew such recipes that much early, an in-game check at a trainer is still to do, and 1 for the few recipes that come with the profession (SkillLineAbility `AcquireMethod` 1, `ingest.ACQUIRE_WITH_SKILL`: Rough Sharpening Stone, Bolt of Linen Cloth, ...; no trainer lists them, `train_cost` 0); 0 when nothing says, and `Recipe.required_skill` then falls back to `trivial_low` (yellow, never below the real requirement). It reads 0 for trainer recipes in older databases until the next game data update. What teaches a recipe is `recipes.source` (revision 0019, `ingest.learn_sources`): `recipe` when an item teaching its spell can be traded or is one a vendor sells (Forever binds most vendor-sold recipes on pickup; `data/forever/vendor_recipes.csv` lists the recipe items spawned vendors sell without a condition, limited stock included, and `vendor_items.csv`'s count too), `bop` when every such item binds on pickup or is a quest item and no vendor sells it (looted or earned: 657 of Forever's 2025 crafts), `trainer` when no item of the game teaches it (ItemEffect also names items ItemSparse lacks: they teach nothing); `trainer` in older databases until the next game data update. **Where to get a recipe** (`RankResponse.learn`, recipe id -> `LearnOut`, only for the results showing "not learned": a craft or enchant nobody selected has learned): its `source`, `Recipe.required_skill` and each item teaching it (`recipe_items`) with its places (`item_sources`, `store.load_recipe_items`), places serving only the other faction left out. The places come from vmangos (vanilla 1.12): spawned vendors without a condition, quests (`<UNUSED>` titles left out; placed where the giver stands, else the zone they are filed under), and the `vmangos.MAX_DROPS` likeliest spawned creatures, chests and containers (a "more" row counts the rest; over `WORLD_DROP_AT` creatures is one "world_drop" row, the chests left out). A vendor row also carries its zone map's `area` and where on it it stands (`map_x`/`map_y`, from its first spawn in its zone; 0 in an instance). Forever's own recipe items (853 of its crafts) have none, and the tooltip says what `source` tells. Zones are guessed from the client's overlapping zone map boxes (`ingest.spawn_zone`, about two thirds agree with the zone vmangos files a giver's quests under). Recipe output count comes from `SpellEffect.EffectBasePointsF` and is only spot-checked. **Which recipes give points**: `recipes.num_skill_ups` (revision 0025) is DB2's `NumSkillUps`, and 0 for a craft or enchant with no thresholds at all (0/0: Forever's First Aid Kit, Toxin Study and camp furnishings, which the game shows grey); `Recipe.num_skill_ups` 0 makes `can_skill_up`, `_chance_at` and `expected_skill_ups` give nothing, while 0/0 on an engine `Recipe` built by hand still means "unknown, a point a craft" (under the cap: `can_skill_up` checks the cap first). `recipes.cooldown_ms` (revision 0025, the optional SpellCooldowns table: the longer of RecoveryTime and CategoryRecoveryTime, the DifficultyID 0 row first) keeps a recipe with `Recipe.slow_cooldown` (at least `engine.CLIMB_COOLDOWN_MS`, an hour: the transmutes, Mooncloth) out of every climb (`Market._candidates`, `service._later_recipes`, `can_start_climb`); the gold list still ranks it. Both read 1 and 0 in older databases until the next game data update. `recipes.cast_time_ms` (SpellMisc -> SpellCastTimes, the DifficultyID 0 row) and `recipes.station` (SpellCastingRequirements' SpellFocusObject name as `timing.station_kind` spells it: anvil, cooking_fire, loom, ...) read 0 and "" in older databases until the next game data update. WoW: Forever adds stations vanilla never had (spinning wheel, sewing machine, tanning rack, loom, master forge, iron oven, alchemy lab, ...): vmangos has no positions for them. Until we learn how they work they are `timing.DEPLOYABLE`: set down where the crafter stands, so never a trip and never `missing`; `Timing.deployed` lists them and the UI names them.
- **Rankings are sessions.** With a time model, `service.search` ranks each recipe as a session of the user's `TimeConfig.batch` crafts (`Market.rank(crafts=)`, timed by `service.session_model`: batch 1, the whole session at once), so cost, revenue, profit, steps and tree are the session's, the bounds apply to them, and `RankResult.details` spells out the route; `/api/evaluate` without `copies` or `city` gives exactly the ranked result (with the user's choices), so the expanded row (`SessionDetails`) shows its own result and asks the server only for other copies or another crafter. Without a time model (CLI `rank`) a result is one craft.
- **The gold list.** Making gold sells every way (`exits` always all three; no Sell via) and shows two ways to sell side by side, so nothing asks how to sell: **Safe profit** (`RankResult.safe_profit`/`safe_exit`, `service.safe_profit`: the better of a vendor and disenchanting, or an essence conversion's sale (`convert`: enchanting materials sell, so a conversion is never capped)) and **Auction profit** (`ah_profit`, `service.ah_sale`: whichever exit pays best, the AH sale counting on as many units as the market has shown it takes (`ah_depth_units`: the more of those seen sold over the week and those listed at or under the sell price, a crude depth until a model of what sells replaces it), the rest (`ah_excess_units`) at the best other exit; None when it can't be sold there). `likely_profit` (`service.likely`) is the better of the two, so it ranks by default (`sort=likely`, `altarmy.search.gold.sort`). Its headers rank by `safe` and `ah` (`service.by_safe`, `by_ah`: best first, or worst first with `/api/rank`'s `order=asc`; those the way isn't open to last either way), each ordered per request over the cached ranking; there is no Sort select (`roi`, `spend`, `all_sell` and `profit_each` stay in the API). Its table (`ResultsTable` `rankBy="gold"`) shows Recipe with a line under it (profession, crafter, crafts, spend, an orange "slow: ~N days" when `slow`), Safe profit (vendor, disenchant with its materials on hover, or "essences sell") and Auction profit (`lib/selling.ts`' `depthNote`: "market takes ~D of M", orange under half, "no buyers shown yet", else "N listed · you add M"; `ahCount` on hover: how it was counted and what all sold would make), the better in bold, the other muted, a dash where a way isn't open; both headers sort on the server (`onGoldSort`), and another click on the sorted one reverses it (`altarmy.search.gold.order`); below `xs` both figures go on one line under the recipe. There is no sale verdict any more (the old "Will it sell" said unproven on nearly every row on young scan data): `service.verdict` survives only for the coach. The expanded row (`SessionDetails` with `market`) shows the copies with the session's crafts, investment and net profit beside them (no skill points), then three sections: Market, closed, its header summing the plan up (`MarketSummary`, `lib/market.ts`' `headerSummary`: what an AH sale counts on and break-even, else how it sells, plus the bought item most of the cost goes on when its market has a cue) (`MarketSection.tsx`: the plan as a strip of items to pick from, `marketItems` (you buy, costliest first, an item bought by several branches summed; you make; you sell; if disenchanted), each with at most one `cue` (short, not listed, floods, thin, then a move of 5% or more from the usual price after 3 days of scans, coloured by whether it hurts the plan); the picked one's headline (what selling counts on, what buying up the ladder costs with `walkLadder`, a vendor's price, what crafting saves); then on a click Show the order book (`MarketCharts.tsx`' `DepthChart`: an SVG staircase of the levels, the plan's units inserted or shaded, `lib/depth.ts`; for an AH output an If I undercut switch to `ProfitChart`; `LadderTable` with You buy; `seenSold`) and More about (tabs: Ways to sell, Sales seen, How we count), both remembered (`altarmy.market.book`, `.more`); the default item is the output, or the likeliest disenchant material when that is how it likely sells; `useMarket`'s `focus` goes in `lib/marketFocus.ts`' `MarketFocus`, so an `ItemLink` in the steps or flow chart of an item the section shows is a button opening it on that item; price history is not drawn yet), Flowchart, open, and Steps, closed (`StepList` grouped under each character as the skill workspace's checklist, Detailed view above, Copy steps below: `SessionDetails`' `StepsPanel`, `lib/skill.ts`' `stepsText` with the details when detailed): no Steps/Flowchart switch, and the AH sell step says the floor under which another exit pays more, the break-even and what was counted on (`floor`, `breakEven`, `countedOn`; `/api/versions`' `ah_cut`, `useAhCut`). Include recipes I could learn sends `unlearned=train`. A realm nobody has scanned shows Upload your scan over the list; one watched under 3 hours this week a dismissible notice (`altarmy.notice.unwatched.<auction house>`).
- **The gold coach (gated).** `service.coach_pick` picks the first craft by likely profit whose sale is at least likely with no buy flag, that counts on no units beyond the market's depth, rests (on the AH) on at least `THIN_UNITS` listed and likely makes `PICK_FLOOR`, else says why none (`CoachNone`: `nothing`, `below_floor` with the surest craft, `all_thin`, `no_watched_sales`, `none_sure`). Nothing serves it yet: `scripts/replay_coach.py` (read-only, never migrates) prints each scanned house's pick and top results by likely and all-sell profit, the evidence for whether the coach card ships at all.
- **Skill-up runs.** With `runs` (`/api/rank` and `/api/evaluate`, in the rank cache key, only with `skill_crafters`), each recipe is ranked as the final crafter's run of it, not the batch (`service.search(skill_run=)`, `Market.rank`/`evaluate(skill_run=SkillRuns)`): the first run of the cheapest climb up the profession that starts with it (`engine.Climb`, `plan_climb`, `Climb.first`; once per market, `Market._climb`). Its markets are narrowed to the profession (`service._market(scope=)`, `skill_scope`: `engine.profession_closure`, the profession's recipes and every recipe making their reagents, however deep, about 500 of 2,400; exact, since `Market._obtain` only reaches recipes through `_by_output`), reuse the base market's flips (`Market(flips=)`) and share its climbs (`Market(climbs=)`, `engine.ClimbStore`: one solve per climber, profession, ceiling and candidates, so city groups pricing them alike share it); `later_recipes` and `skill_scope` are worked out once per base market (`service._derived`, kept until prices move; `later_recipes`' key must name every input it reads); city-group markets are built only when a plan reaches them (`service._Markets`); a climber nothing can give a first point gets no runs before any of that (`engine.can_start_climb`). `Climb._cheapest_from` inlines `_Usable.cost` and `_cheaper` (a change to the run's cost goes in both; a test compares them over random climbs). The climb is a dynamic program over integer skill levels from the climber's skill to their cap (or a skill nothing gives a point at; the cap is the version's `max_skill`, not the uploaded one: the climber is assumed to train each profession rank as they come to it, but only those their level allows (`GameVersion.trainable_cap`; the hypothetical climber is the version's top level), `api._trained_up`/`service.trained_up`, and the skill workspace's single column reminds them beside the card whose run reaches a rank's training skill: `GameVersion.profession_ranks` via `/api/versions`, `lib/skill.ts`' `ranksToTrain`): a run of a recipe from s to t costs its expected crafts (a point at skill l takes 1/p(l), p as `skill_up_chance` with the crafter's talents, so the expectation is exact) at what a craft counts for: its net cost (spent less what selling what it makes brings back, per craft of a run of its `useful_crafts`, so up the AH's ladders: `Candidate.cost`, the real copper: a craft that earns lowers the climb's cost; no floor since the Master Chef case, where it hid most of Cooking's profit and left Cheapest dearer than Recommended), plus what a craft is worth to the climber (`SkillRuns.craft_value`, default `CRAFT_VALUE` 50c), plus the spare materials bought for it (`SPARE_Z` standard deviations of its crafts at the cost, none for a craft that earns: what makes short detours pay for themselves), plus the effort of its low-chance points (the craft value x (1/p - 1)^2 a point: one exchange rate between copper and crafts at every level, which no other candidate moves), plus its pattern (`Market(learn_costs=)`, from `service.climb_learn_costs` via `api._climb_learn_costs`; unknown prices are counted apart, fewer first). A recipe is crafted only at a skill it gives a point at with at least `SkillRuns.min_chance` (`engine.MIN_CHANCE`, 10%, for Recommended and Trainer only; 0 for Cheapest), except at a skill nothing gives one that often: there any recipe may be (a dead end with the cutoff), and past it the cutoff applies again (`_Usable.reach`). Only plans are chosen by the craft value, the spares, the effort and the cutoff; no price includes them (`ClimbPlan.spent_by` is the real copper). The candidates are the profession's recipes not grey for the climber (`Market._candidates`; from 0 if known, else `required_skill`) plus `service.later_recipes`: those they can learn on the way to the cap (unless `unlearned` is "none"), each priced with the climber at that skill and everything else as it is. A run longer than `RUN_CEILING` (100) crafts is one run to the plan and goes on as several (`"ceiling"`); a climb that comes back to a recipe after another counts its pattern once in `ClimbPlan.cost` and `spent_by` (`engine._repeats`), though the DP itself, whose state is the skill alone, weighs each leg's pattern (an approximation that changed no plan on the dev data). A recipe the climber can't use at their skill is no run (`evaluate` returns None). A run stops where the climb goes on with another recipe (`"rival"`, `overtaken_by` that recipe's output: the plan's own next run), the recipe turns grey (`"trivial"`, whatever follows), or the cap (`"cap"`); `stop_skill` is where it ends (a run's `skill_ups` are the points it climbs, `stop_skill` less where it starts, Working Overtime's share of them its share of what the crafts are expected to give), and `crafts_quantile` the crafts that get there four times in five (exact over the per-craft chances). `Result.climb_cost`/`climb_unknown` are the climb's cost with this run first, `climb_after` its later runs (`SkillRun`s) and `climb` the whole `ClimbPlan`; `service.by_skill` orders runs by the climb (`RankResult.climb_cost`, None with an unknown pattern). `Result`/`RankResult` carry `stop_skill`, `stop_reason`, `overtaken_by` (and `overtaken_by_item`, its output's item id, in `items`), `crafts_p80` and `reach_chances` (`engine.reach_chances`: the chance of reaching `stop_skill` after each of 1, 2, ... crafts, to twice `crafts_p80`, at least `REACH_MORE` past it and at least to the crafts that get there `REACH_TOP` (95%) of the time) and `RankResult` the recipe's `learn_skill`, `trivial_low`, `trivial_high`. `/api/evaluate` with `copies` plans those copies instead. `engine.KEEP_EXIT` (`keep`, value 0, last of `exits_for`) keeps what no vendor buys, only for `skill_crafters` and only when among the exits. - **Reputation discounts.** A vendor charges a buyer less for their standing with the vendor's faction: `GameVersion.reputation_discounts` (Forever: vanilla's 10% from Honored, nothing more at Revered or Exalted), added to Bartering's percent and the unit price rounded up (`engine.vendor_price`; adding rather than multiplying is an assumption until a Forever vendor's price is compared; vanilla's further 10% for PvP rank 3 is not modelled). A faction not listed is Neutral. The vendor's faction is per vendor, not per city (`vendor_reputations` in the presets, from vmangos: gnome vendors in Ironforge and Stormwind, troll vendors in Orgrimmar; a vendor of any other faction discounts nothing), so the price needs a city: `Market._vendor_unit` takes the best discount among the time model's city's sellers of the item (`Node.rep_discount`, `Step.rep_discount`), and the route buys at a vendor who gives it (`engine.vendor_holders` into `Block.vendor_sellers`). Without a time model (CLI `rank`) or presets (TBC) nobody gets one.

Without standings that count there is one group: the plain path, at its cost. - **`auction_houses.price_version`** moves whenever the house's prices changed: `prices.record_snapshot` bumps it when it moved a current price (not for a quarantined or news-less scan), the merge when its 7-day columns changed. - **Prices are per auction house** (`auction_houses`: version, realm, faction; faction `""` = one shared by both factions (none on Forever since revision 0009: its houses are per faction); realm `""` = the unnamed one, for prices set without a realm). A selection's auction house is its faction's, else its realm's shared one (`prices.find_auction_house`). Sources: Alt Army's scans (`altarmy`, Forever), Auctionator uploads (TBC), manual/CSV. Forever reads only `altarmy` and hand-set snapshots (`prices.FIRST_PARTY`); revision 0014 deleted what AHledger and Auctionator had recorded for it. Every source records a `price_snapshots` row; `price_observations` get only news and move `price_current`, which the engine reads; the newest `seen_at` wins whatever the source, so a manual price holds until a later scan, and a price from another source replaces a scan's ladder. An Auctionator item was seen at the scan time if its last day is the scan day, else at the start of that day; an Auctionator key ending in the faction means a split house. `price_daily` comes from Auctionator's h/l/a or a scan's market price and is pooled across uploaders (min low, max high, max available). Observations older than 180 days are pruned after each upload and by the prune job; snapshots `price_current` points at are kept. Money columns for prices are `BigInteger` (copper exceeds 2^31).
- **The order book (Forever).** An Alt Army scan lists every auction; the addon pools them per item into price levels (unit price = buyout over count, rounded up; listings without a buyout are counted only; items are keyed by item id alone, so random-suffix gear shares its base item's ladder; sellers are never stored). `price_current.ladder` holds the newest scan's ladder (`book.encode`), `listed` whether that scan had the item (an item missing from a scan is unlisted: no AH buy option, and it sells at what it used to go for), `market_price` the price 15% into the listed units. Only complete scans exist: the addon drops one the auction house closed on. A level's `age` counts the scans it survived; a level of age 0 under half the 7-day median is left out of what plans buy (a stray cheap listing is gone before anyone gets there) but shown in the item's tooltip. Sales are inferred between two scans at most 30 minutes apart (`book.sold_between`); an emptied market says nothing (counted as cancelled). So sales are seen only while someone scans back to back: `sale_rate` counts what was seen, a lower bound, and the price confidence weighs "no sales seen" by `prices.watched_hours` (an unwatched house's missing sales say nothing; a stale unlisted item keeps its last price, which the confidence calls low). The scan's time is the game server's (`GetServerTime`), so no local day is compared.
- **Buy vs sell price.** Forever: reagents are bought up the item's ladder (`Market.books`; `Market.prices` holds its cheapest counted level), and a craft sells at `prices.book_sell_price`: the lower of the market price (while listed) and what the item goes for (`sale_price`, else `median_7d`). TBC and hand-set prices: `Market.prices` is `price_current.price`, the cheapest listing, and `Market.sell_prices` the lower of `price` and `median_7d`, except for `manual`/`csv` snapshots, used as they are. `median_7d` is the median of the item's daily medians over its latest 7 days with data within 30 days (not 7 calendar days: one player's sparse scans would leave a lone spike as the only sample); `scans_7d` counts those days. `price_daily.median` = median of the day's low, high and that UTC day's accepted scan prices (clamped). The merge fills them; until then the sell price is the price. `sell_cap` and `feed_tables` are unused since revision 0014 and dropped by the next revision.
- **Quarantine.** Only uploads are screened (`trust=None` records a scan unscreened). A scan is quarantined when at least 20 of its fresh prices (an Alt Army scan's market prices) can be compared with a baseline (`median_7d` with `scans_7d >= 3`) and more than `0.1 + 0.2 * trust` of them are over 4x off either way (real TBC scans: at most ~5%). An Alt Army scan taken at most 30 minutes after another is also quarantined when it has under a quarter of that scan's price levels (`prices._breaks_off`, from 50 levels on; the share is a guess until real pairs of scans are measured). A quarantined snapshot is a `status='quarantined'` row only: no observations, no `price_current` or `price_daily` change; the merge ignores it.

- Characters and mail: `Market` gets the selected characters as `engine.Crafter`s and costs every craft *at a character* (`Market._obtain`): each reagent is bought there, or crafted by any character who can (learners, or with no learner, whoever `unlearned` lets: `engine.can_learn`) and mailed over if that is someone else. The final crafter is whichever gives the best profit. Postage is `MAIL_POSTAGE` (30c) per attachment, one stack each (`items.stack_size` from `ItemSparse.Stackable`; older databases read 1 until the next game data update). A disenchant is free if the final crafter enchants, else the output is mailed to the best enchanter; with no enchanter at all the disenchant exit is dropped. Postage is in `cost` and shown as `mail` steps (the flow chart leaves mailing out: its edges go straight from one character to the other); steps carry `who`. `engine.plan_steps` (a `Result`'s `steps`, planned when first read, so a ranking never schedules results nobody looks at) orders them dependencies first and then per character (`engine._schedule`): each does all their buys, then crafts, then mails before another takes over, whoever can finish outright first, so a character is revisited only for what waited on someone's mail. Without crafters (CLI `rank`, or browsing without characters on the web) one unnamed character does everything, so nothing is mailed; the results table shows "anyone" as the crafter. Costs are whole batches (spares from multi-output crafts are not credited). Soulbound items (`Item.tradable` False: `items.bonding` 1 or 4) are never mailed, so only the character who needs such an intermediate crafts it, a soulbound craft is disenchanted only by its crafter, and it gets no AH exit. One `Memo` serves a whole `rank()` (keyed on item, quantity, character and depth, not the ancestors): chains stop at `MAX_CHAIN_DEPTH`, which also ends cycles, and a recipe consuming its own output is skipped.
